# Валидность кэша транскрипта: отпечаток таймлайна, ключ по sequenceID, привязка к бэкапам

**Дата:** 2026-07-28
**Статус:** утверждено пользователем (brainstorming, ответы: C → B → A → C → «A с привязкой к B» → A)

## Проблема

Кэш транскриптов уже существует (`_llm_transcript_cache.json`, per-sequence, персистентный), но:

1. **Ручные правки пользователя в Premiere** (резы, сдвиги, удаления мимо панели) не детектируются. Транскрипт молча остаётся «валидным», хотя тайминги уехали — тихая порча результатов транскрипт-зависимых инструментов.
2. **Ключ кэша = имя секвенции**: переименование теряет транскрипт, одинаковые имена коллидируют. Стабильный `sequenceID` Premiere не используется.
3. **Бэкап-секвенции** (создаваемые нашими же инструментами перед деструктивными операциями) не наследуют транскрипт — откат на бэкап требует повторной транскрибации.

Собственные правки панели проблемой НЕ являются: ripple-резы уже пересчитывают тайминги (`applyRippleDeletionsToTranscript`), неопределённые сдвиги ставят `possiblyStale` (`markTranscriptStale`).

## Утверждённые решения

| Вопрос | Решение |
|---|---|
| Реакция на невалидность | **Мягкий гейт**: предупреждение + confirm перед запуском инструмента; не жёсткая блокировка |
| Что инвалидирует | **Только аудио-дорожки**; правки видео транскрипт не трогают |
| Когда проверять | **Гибрид**: индикация в polling (~4с) + контрольная проверка перед запуском инструмента |
| Где считать хэш | **В host (ES3)** — через bridge летит короткий hex, не сырая строка |
| Ручное сохранение/загрузка | **Не нужно**; вместо этого авто-привязка транскрипта к бэкап-секвенциям |
| Ключ кэша | **sequenceID**, fallback по имени для legacy-записей с миграцией на лету |

## Дизайн

### 1. Отпечаток аудио-таймлайна (host, ES3)

Новая функция в `host/premiere.jsx`: перебор всех аудио-дорожек активной секвенции; для каждого клипа строится строка:

```
trackIdx|mediaPath|start.ticks|end.ticks|inPoint.ticks
```

Строки клипов конкатенируются (разделитель `;`, порядок обхода детерминированный: дорожки по индексу, клипы по порядку в дорожке), результат хэшируется **FNV-1a 32-bit** → hex-строка (8 символов). Тики, не секунды: точные целые, без сравнения float.

- Отпечаток (`audioFp`) и `sequenceID` добавляются в ответ `getSequenceRegionInfo` (лёгкий poll-вызов) и в полный снапшот таймлайна.
- ES3-ограничения: без `Array.prototype.map/forEach`, битовые операции FNV-1a доступны в ES3 (`^`, `*`, `>>>0` — умножение через сдвиги/imul-эмуляцию, т.к. 32-битное переполнение в ES3 надо контролировать вручную).
- **Известное ограничение V1:** mute дорожки/клипа и уровни громкости в отпечаток не входят — они не двигают позиции. Задокументировать в описании функции.

### 2. Хранение и ключ кэша

- В entry транскрипта добавляются поля:
  - `timelineFp: { hash: string, at: timestamp }` — отпечаток за **транскриптом** (segments), записывается при завершении полной транскрибации;
  - `audioAnalysis.analyzedFp: string` — отпечаток за **аудио-анализом**, записывается при транскрибации (если анализ построен) и при «⚡ Анализ аудио». Раздельно, потому что аудио-анализ обновляется независимо («⚡ Обновить анализ» освежает только его) — зеркально существующему паттерну раздельных `analyzedRegion`;
  - `seqName: string` — имя для отображения (ключом больше не является);
  - `seqId: string` — дублирует ключ для самодостаточности entry.
- Ключ кэша в `_llm_transcript_cache.json` = **sequenceID**.
- Поиск (`findTranscriptEntry` в `client/shared/context-store.js`): сначала точное совпадение по ID → fallback по имени (нормализованному, как сейчас) для legacy-записей. При находке по имени и известном ID — entry перепривязывается к ID (одноразовая миграция на лету, старый ключ удаляется).
- Все существующие вызовы, передающие имя секвенции как ключ, переводятся на пару (ID, имя).

### 3. Проверка валидности

**Polling (~4с, существующий setInterval в panel.js):**
- `getSequenceRegionInfo` теперь возвращает `audioFp` и `sequenceID`.
- Панель сравнивает `info.audioFp` с `entry.timelineFp.hash` (транскрипт) и `entry.audioAnalysis.analyzedFp` (аудио-анализ).
- Mismatch → LED «транскрипт устарел — таймлайн изменился». **Только LED, без карточных гейтов**: существующий механизм гейтов (`toolsUpdateCards`) жёстко блокирует кнопки, что противоречит утверждённому мягкому гейту — кнопки остаются живыми, честность обеспечивает confirm перед запуском.
- Отсутствие `timelineFp` у legacy-entry → считается «неизвестно», предупреждений нет (не блокировка).

**Перед запуском транскрипт-зависимого инструмента:**
- Свежий host-вызов отпечатка (не полагаться на последний poll — окно 4с).
- Mismatch → confirm-диалог: «Таймлайн изменился после транскрибации. Тайминги транскрипта могут не совпадать. Продолжить по устаревшему транскрипту?» [Продолжить / Отмена]. При отмене — подсветить кнопку транскрибации как рекомендованное действие.
- Проверяемые инструменты (вкладка Инструменты): по `timelineFp` — fillers, profanity, speakers, reels, chapters, subtitles-anim, subtitles-static; по `audioAnalysis.analyzedFp` — silences, jumps (их proposal строится из кэшированного audioAnalysis, ручные правки сдвигают его координаты так же). Не проверяются: trim-edges, gaps, multicam, loudnorm, markers-export, backups (работают по свежему снимку/без кэша). Montage из чата — вне объёма V1 (LED предупреждает).

### 4. Синхронизация после собственных правок панели

После успешного apply (ripple-резы, edit plan, любая операция, вызывающая `applyRippleDeletionsToTranscript`):
1. Панель уже пересчитала тайминги транскрипта.
2. Сразу запросить у host свежий отпечаток и записать в `entry.timelineFp`.

Наши правки не создают ложного «устарело». `markTranscriptStale` (unknown shift) остаётся без изменений: пересчёт там невозможен, отпечаток закономерно разойдётся, и мягкий гейт сработает честно — это желаемое поведение.

### 5. Привязка транскрипта к бэкапам

При создании бэкап-секвенции (дубликат перед деструктивной операцией): скопировать entry текущей секвенции под `sequenceID` бэкапа (глубокая копия, обновить `seqId`/`seqName` в entry). Отпечаток дубликата идентичен оригиналу на момент копирования — транскрипт бэкапа валиден сразу.

Откат пользователя на бэкап = транскрипт работает без повторной транскрибации.

### 6. Тестирование

**Unit (Node, `tests/*.test.mjs`):**
- FNV-1a: известные векторы (пустая строка, ASCII, кириллица/UTF-16 код-юниты — зафиксировать, что хэшируем код-юниты строки, т.к. ES3).
- Сборка строки отпечатка из эмулированных структур треков/клипов: детерминированность, чувствительность к каждому полю, нечувствительность к видео-дорожкам.
- Миграция ключей: находка по имени → перепривязка к ID, старый ключ удалён.
- Копирование entry для бэкапа: глубокая копия, обновлённые seqId/seqName.

**Live (CDP):**
- Транскрибация → ручной рез аудио в Premiere → в течение ~4с LED «устарел» → запуск fillers даёт confirm → повторная транскрибация возвращает валидность.
- Правка только видео-дорожки → LED валидности не меняется.
- Наш собственный ripple-рез → LED остаётся валидным (отпечаток обновился).

## Вне объёма (V1)

- Учёт mute/громкости в отпечатке.
- Частичная ре-транскрибация только изменённых областей.
- Именованные версии/снимки транскрипта на секвенцию.
- Ручной экспорт/импорт транскрипта в файл.
